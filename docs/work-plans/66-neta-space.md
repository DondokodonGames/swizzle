# WP66: ネタ空間 — 「何度考えても似たパターンに収束する」の正体と対処

**問題**: ネタを考えるたびに似た遊びに収束する。権利の問題より根が深い。

## 実測（2026-08-18）

`npm run ai:neta:space` / 一時解析スクリプトによる計測。

| 指標 | 実測 | 意味 |
|---|---|---|
| ネタ総数 | 延べ 2384 → **ユニーク 1428** | **956件（40%）がファイル間のコピー**。同じネタを何度も見るのは在庫が重複しているから |
| 文面の近傍重複（ユニーク間、3-gram Jaccard≥0.3） | **1.8%** | 文章としては被っていない。「似ている」の正体は文面ではない |
| 遊びが読み取れないネタ | **690件（48%）** | idea に指の動詞が書かれておらず、分類器が既定値に落ちる |
| 成功回数の指定 | 3回=1301 / 5回=525（**77%**） | 数字も収束している |
| 既存800本のメカニクス分布 | C族230 / A族189 / F族171 に偏り | 作った側も同じ場所に寄っている |
| G族（1台で2人） | **ゲーム0本**（ネタ13件） | 飲食店設置で最も価値が高いのに空 |
| H族（射幸/演出） | **ゲーム0本・ネタ0件** | コイン投入動機に直結するのに空 |

## 収束の原因（3つ、いずれも発想力の問題ではない）

1. **ネタが遊びを指定していない（48%）**
   「妖精を捕まえる」のように題材だけ書かれたネタは、生成側が既定の遊び
   （タップ/タイミング）に落として作る。結果、**題材だけ違う同じゲーム**が量産される。
2. **mechanic 欄の語彙が入力種別だった**
   `tap` / `drag` / `swipe` / `flick` は「指の入力方法」であって遊びの型ではない。
   7語彙では遊びを区別できないので、書いても収束を止められなかった。
   → 40+IDの遊びの型（`MECHANIC_FAMILY`）に変更。
3. **在庫が見えないまま自由連想していた**
   人間もLLMも、白紙から考えると馴染みのある型（タイミング/連打）に戻る。
   空きセルを先に見れば、そもそも別の場所から考え始められる。

## 対処

### `npm run ai:neta:space`（新設）

既存800本（台帳の人間確定メカニクス）とネタ帳（重複排除＋分類）を**同じ物差し**で数え、
族ごとの埋まり方・一本も作っていないメカニクス・次に狙うべき10セルを出す。

- 分類器は `src/ai/code/mechanicClassifier.ts` に切り出し、台帳生成と共有（単一の真実の源）
- 既定値に落ちたネタは畳み込まず「未分類」として別に数える（畳み込むと地図が嘘になる）

### ネタ生成プロンプトの変更（`CHATGPT_NETA_PROMPT.md`）

- 「考え方の手順」を追加：**空きセルを選ぶ → その遊びを考える → 題材は最後**
- idea に**指の動詞を必ず書く**ことを明記（48%問題への直接対処）
- `mechanic` の語彙を 40+ID に変更

## 既存800本も同じ収束をしている（2026-08-18 追加計測）

ネタだけでなく、**作り終えた800本にも「題材だけ違う同じゲーム」が埋まっている**。

| 測ったもの | 結果 |
|---|---|
| 無作為な2本のコード骨格一致度 | **0.35**（全ゲームが同じAPIを同じ順で叩くためのベースライン） |
| 同一slugのグループ | **117群 / 349本（43.8%）** |
| 機械検出した重複群（コード0.45↑ or 操作文0.35↑が過半） | 36群 / 102本 → **余剰66本** |
| 手で読んだ範囲の実態 | gravity-flip 12本＝1つの遊び（数値と世界観違い）、chain-reaction 9本、tower-stack 5本、firefly-catch 4本、neon-snake 4本 … |

機械検出（66本）は下限。chain-reaction のように実装は違うが遊びは同じ群を拾えないため、
実態は **66〜232本（同一slug余剰の上限）** の範囲にある。

### 書き換え計画がこの重複を温存する構造になっている

WP56 の「守ること」は **メカニクスと勝敗条件を変えない**と定め、差別化は
theme / variation / spice（世界観・プレッシャー型・スパイス）で行う。
gravity-flip 12本の割当を見ると、全て `camera_run` のまま、世界観だけ
おばけ屋敷 / ダンジョン / 学校 / スタジアム / サーカス / 忍者屋敷 / キッチン / 雪山 …と振られている。

つまり書き換えを完走しても **「タップで重力反転して隙間を抜ける」ゲームが12本残る**。
磨きは効くが、収束は解けない。

### 収束はメカニクスの層では起きていない（2026-08-18 追加計測）

「gravity-flip や chain-reaction のようなメカニクスに収束しているのでは」という問いを計測した。
**そもそも gravity-flip / chain-reaction は slug(企画名)であってメカニクスではない**
（台帳上は前者が `camera_run`、後者が `timing_one_shot`）。

| 層 | 実測 | 状態 |
|---|---|---|
| メカニクス | 38種 / 1IDあたり平均 21.1本・**14.9 slug** | 健全 |
| slug | 568種 / 117群 349本が重複 | **ここが重複の層** |

`camera_run` 30本の中身は 16 slug に分かれ、遊びとしては明確に別物:

```
gravity-flip  タップで重力を反転
bridge-cross  隣の石をタップして跳ぶ(ひび石は踏むと崩れ落下)
crowd-surf    タップした方向へ飛び、次に伸びた手に着地する
ramp-jump     ランプ端でタップしてジャンプ。合計飛距離を稼ぐ
torch-relay   タップで走者を加速 / 右スワイプで次の走者へ炎を渡す
```

つまりメカニクスIDは「**画面が自動で進み続ける中で操作する**」という舞台の枠組みのラベルであって、
遊びそのものではない。誤分類ではなく解像度がひとつ粗いだけ。

**帰結**: 重複の解消は「同じ遊びを別の遊びにする」ことが目的で、**メカニクスIDの変更は手段にすぎない**。
`camera_run` が16通りの遊びを抱えられている以上、同じIDのまま別の遊びにしてもよい。
下の振り替え案は空きIDを機械的に順番に割り当てただけなので、**そのまま従わないこと**。

### 提案: 重複の余剰を空きセルへ振り替える

`npm run games:dup`（新設）が重複群と振り替え案を出す。`--csv` で
`docs/work-plans/ledger/dup-conversion-proposal.csv` に書き出す（**提案であって確定ではない**。
振り替え先は在庫の薄い順に機械的に割り当てているので、人間が遊びとして成立する組み合わせに直すこと）。

重複を「消す」のではなく、**空きセル（G族=1台で2人 / H族=射幸演出 / freeze / pinch_zone）へ変換**する。
在庫が減らず、いちばん足りない場所が埋まる。実施するなら WP56 の「メカニクスを変えない」を
**重複群に限って解除**する必要がある。

## 次に効く手（未着手）

- **ネタ帳の統合と重複排除**: 23ファイル・956件のコピーを1本化する。
  進捗ファイルがIDで紐づいているため、統合時はID再割当と進捗の移送が要る
- **G族（1台で2人）の新規ネタ**: 飲食店に置く台で最も効く空きセル。
  2人が1台を囲む遊びは、拠点あたりの投入額を上げる方向にも直結する
- **H族（射幸/演出）**: `jackpot_combo` / `near_miss` はコイン投入動機そのもの。
  ARCADE_ART_DIRECTION §3（コイン投入動機の演出規定）と対で設計する
- **生成時のセル指定**: `runFromNeta` が「今どのセルが薄いか」を見て、
  薄いセルのネタを優先的に消化する（現在は id 順）

## ネタの「強さ」は誰も測っていない（2026-08-18 追加計測）

「800本のネタが貧弱なのでは」を検証した。結論は **半分当たり、半分違う**。

### 思ったほど弱くなかったもの

| 測ったもの | 結果 |
|---|---|
| フック（ヘッダー2行目）と操作行の重なり | 中央値 **0.13**、0.35以上は **11本(1.4%)** |

フックが操作の言い換えになっているゲームはほとんど無い。実際に読むと
「震える手でケーブルをなぞる外科医の集中力」「こぼれる寸前で止める最後の一秒」
「電力過負荷寸前の綱渡り、上げすぎたら終わり」のように、一行としては書けているものが多い。

> **計測上の注意**: 当初フックの良し悪しを感情語のキーワードで分類しようとしたが、
> 上記のような良いフックを軒並み「操作説明のみ」に誤判定した。**フックの強さは
> キーワードでは測れない**（この方法での割合は本書に載せない）。

### 実際に弱いもの

| 測ったもの | 結果 |
|---|---|
| **世界観コメントが無い** | **698本 / 87.6%** |
| 遊びの型の偏り | 上位3族(C/A/F)に集中、G族(1台で2人)・H族(射幸/演出)は **0本** |
| 同じ遊びの重複 | **66〜232本** |

一行のフックはあるが、**その先の肉付け（世界観・状況）がほぼ無い**。
題材が薄いまま量産されたので、遊びが同じだと差が出ない。

### 根本: 品質ゲートがネタを一切見ていない

| ゲート | 何を見ているか | ネタを見るか |
|---|---|---|
| `CodeGameValidator` | 権利・API・v3文法（テキストレス等） | ✗ |
| `CodeQualityScorer` | actionFeedback 25 / audioVisual 20 / layout 15 / goalEndings 15 / structure 15 / runtime 10 | ✗（コメントに「concept は採点に使わない — 成果物そのものを測る」と明記） |
| `games:smoke` | 実行時エラー・GAME_END到達・描画反応 | ✗ |

**3つとも実装品質しか測っていない。** だから「迫りくる敵をタップで撃退するシンプルな防衛戦」でも
満点が取れる。弱いネタが弱いまま磨かれて出荷される構造になっている。

### 埋め方の候補

1. **機械で測れる分だけゲートに足す**: 世界観コメントの有無 / 重複セルの検出（`games:dup`）/
   空きセルからの選択（`ai:neta:space`）
2. **ネタ採点器（LLM判定）**: フックの強さは人間かLLMでしか測れない。
   `run-trend-neta.ts` が既に Anthropic SDK を使っているので、同じ経路で
   「800本のフックを採点して弱い順に並べる」ことは実装可能（APIキーが要る）
3. **Wave の工程にフック点検を入れる**: 書き換え前に、その3本のフックが
   「操作の説明」でなく「なぜ面白いか」を語っているかを人間が確認する
